# ARCHITECTURE.md

The reference half of the project guide: what each source set and package is for, how one chat turn and one task run, what is persisted where, what crosses the network, and who may do what. Read it before changing a package you have not worked in.

`AGENTS.md` is the other half and the one every session loads: commands, workflow, testing, git hygiene, versioning. When a file here disagrees with the code, the code wins — fix the stale file in the same commit.

## Source sets

The root Gradle project remains the Loom mod and uses `loom.splitEnvironmentSourceSets()`; one mod (`friendai`) spans `main` + `client`. The included `:engine` Java library is compiled separately and embedded once in the distributed mod jar. Engine owns foundation text/diagnostics/limits/persistence contracts, execution queue/tool contracts, agent turn/planning/prompt/routing and LLM model/protocol/provider logic, game-independent feature policies including speech, and JVM configuration, speech HTTP/model-download, appearance HTTP and persistence adapters. Native speech engines and client audio remain in root/client.

| Source set | Path | Contains | Notes |
|---|---|---|---|
| `engine main` | `engine/src/main/java` | Foundation and persistence contracts, execution, agent and feature policies, JVM config and persistence adapters | No Minecraft, Fabric, optional UI or native audio compile dependency. |
| `engine test` | `engine/src/test/java` | Pure unit tests | Root `test` aggregates `:engine:test`. |
| `engine testFixtures` | `engine/src/testFixtures/java` | Reusable pure fakes | Never included in the shipped mod jar. |
| `main` | `src/main/java` | Pure layers, Minecraft-layer server/common code, resources | The shipped jar's common half. |
| `client` | `src/client/java` | Renderer, screens, HUD, keybinds, voice capture, speech output | Loaded only on the client. |
| `test` | `src/test/java` | JUnit tests and reusable fakes | No Minecraft at runtime. |
| `gametest` | `src/gametest/java` | Fabric GameTest classes plus `GameTestSupport` | Separate mod `friendai-gametest`; entrypoints listed in `src/gametest/resources/fabric.mod.json`. |

## Overview

Bottom-up. The dependency rule is per class/module, not per package: **engine classes must not import `net.minecraft.*`, `net.fabricmc.*`, optional UI libraries or native audio bindings**. `chat/`, `net/` and `perception/` are mixed packages; only the classes named below are pure. JVM adapters live in `infrastructure/`; feature packages depend on ports and foundation contracts, never on infrastructure implementations.

```
root Fabric mod  (server/entity, client source set, bootstrap and adapters)
   |  depends on the game-independent module and embeds it in the mod jar
engine  (foundation, execution contracts, agent, pure feature policies, JVM infrastructure and LLM protocols; later presentation slices)
```

Cross-feature dependencies are explicit and directed, and `PackageDependencyRules` enforces every dependency with positive and negative fixture coverage. Navigation delegates live route digging and bridge-material gathering to mining's `BreakAction` and `MaterialGatherer`; mining uses navigation's path search and executor, so these two adapters share an explicit bidirectional boundary. Acquisition may call creative capability operations, but it cannot construct creative task implementations. Interaction consumes the creative command policy, combat threat checks, and navigation's public entity movement and target APIs; navigation does not construct interaction tasks. Inventory reuses acquisition's tool-requirement data, navigation target/movement APIs, remembered-place queries, and the pure hunger model; container opening and item transfer mechanics are shared through `task/interact/ContainerSession` and `ContainerTransfer`. Animals uses combat threat facts, mining's block matcher and navigation approaches; combat uses inventory equipment helpers, navigation and the pure hunger model; construction uses fire hands for safe clearing; survival composes combat threats, cooking, farming, knowledge observations, mining and navigation support; fire uses crafting, mining and navigation adapters. Feature Minecraft tool adapters may depend on exactly `server/execution/tools/FeatureToolContributor`, `FeatureToolRegistry`, `TaskToolDefinition`, and the nested `TaskToolDefinition.Factory`, `TaskToolDefinition.CallerFactory`, and `TaskToolDefinition.QueueTraits` helpers to register contributions; server runtime services remain outside the feature boundary.

## Pure Java modules

- `engine/.../agent/llm/model/` — `Message`, `ToolCall`, `LlmRequest`/`LlmResponse`, `LlmException`. Invariant: a malformed tool-argument JSON leaves `ToolCall.arguments == null` while `rawArguments` is kept; Gemini's opaque `signature` must be echoed back.
- `engine/.../agent/llm/protocol/` — one class per wire format: `OpenAiChatProtocol`, `OpenAiResponsesProtocol`, `AnthropicMessagesProtocol`, `GeminiProtocol`, `OllamaProtocol`; each has `toWire`/`fromWire` and calls the `JsonHttpTransport` port. Anthropic and Gemini must receive consecutive USER/TOOL messages as **one** user message; malformed arguments serialize as `{}`.
- `engine/.../agent/llm/provider/` — presets and routing as **data**: `ProviderPreset`, `RoutingRule`, `Route`, `LlmProfile`. First glob match wins; base URL precedence is profile → rule → preset. Protocols and presets are registered in `ProviderRegistry.withBuiltins`.
- Root `llm/http/HttpTransport` implements the engine JSON transport port and retains retries only for retryable error kinds, HTTP-status mapping and key redaction; root `llm/LlmClient.complete` resolves the route and delegates.
- `infrastructure/config/` — `ConfigStore` (atomic temp + move, `.bak` on corruption, optional migrations), `ServerConfig` (schema version 16 and clamping validation, including task, agent, place, autonomy, and chunk-loading settings), `ClientConfig` (schema version 4), `VoiceDraft`, `VoiceConfig`, `SecretResolver` (`env:NAME`). Unsupported client settings versions are left untouched and cannot be overwritten. A key typed into a config is stored there in plaintext, so `env:NAME` is preferred; keys are never logged, put in a URL, or included in toasts and error messages, and the settings screen masks them until **Show key** is pressed.
- `engine/.../foundation/text/` — `UserMessage(key, args)` and `UserFacingException`: the only player-facing protocol flowing out of pure layers; `LanguageDetector` (script counts plus a few stopwords, quoted spans and `/commands` ignored) and `LanguageMemory` (commits the first confident sample, switches only after three in a row) learn the owner's language.
- `engine/.../execution/tool/` — `Tool`, `ToolRegistry`, `ArgValidator`, `SchemaBuilder`, `AccessLevel`/`Caller`, `PlanParser`, `InventoryAccess`, `StopScope`. `ToolRegistry.run` never throws: unknown/disabled tool, wrong access, bad JSON or schema violation become `ToolResult.error`. Access is ordinal `GUEST < TRUSTED < OWNER`; the default minimum is `TRUSTED`. Gameplay contributors live with their feature; the ordered server bootstrap is `server/agent/tools/FriendaiTools`.
- `engine/.../agent/turn/` — `CompanionBrain` (the agent loop, one principal per turn), `PromptBuilder`, `ConversationMemory`, `AccessResolver`, `BrainEvent`, `AgentSettings`, and the ports the agent layer plugs into the loop: `GoalSource` (the goal shown in the prompt) and `PlannerPort` (consult the planner, queue its plan). `SkillTurnSession` is the boundary to the root instructions adapter. Invariants: at most one LLM request per turn; a generation counter silently drops late responses, including a planner proposal that arrives after a stop; trimming drops whole leading USER turns so history never starts with a tool result.
- `agent/` — the cognitive layer above the task queue, all pure Java. `goal/` (`GoalBoard`: one primary and up to three background goals with criteria that may carry a queue `Guard`, at most five 160-character lessons, a replan budget; `GoalSave` encodes the target JSON payload; `GoalService` uses the independent owner `GoalRepository`, so goals outlive the entity), `route/` (`TurnRouter` picks chat, action, goal, recovery or event from deterministic English and Russian vocabularies in `agent/intents_*.json`, defaulting to action with every tool group), `tools/` (`ToolCatalog`: every tool belongs to a `ToolGroup` and may carry a "when to use" hint; core tools are always visible, `request_tools` unlocks a group for the turn; a tool missing from the catalog is always visible, and a GameTest fails the build until every registered tool has an entry), `prompt/` (`PromptSection`, `PromptAssembler` with a character budget that cuts tool hints first, then rules, memory, mission and state, and never identity, speech, working method or role; `DefaultSections`, `MissionText`), `verify/` (`OutcomeChecker` turns before/after `WorldSnapshot`s into at most eight facts), `recover/` (`RecoveryAdvisor` classifies a failure text and suggests remedies not yet tried; `FailureHandler` appends facts and diagnosis to events and spends the goal's replan budget), `plan/` (`Planner`, `LlmPlanner` with 1–4 total attempts (`agent.plannerRetries`, default 2) and a per-attempt timeout, optional native JSON mode, redacted rejected assistant turns and specific repair instructions; truncation increases output room and oversized plans request a shorter draft, while request failures never retry; `PlanFailure` carries a code, bounded diagnostic and attempt, `PlannerException` transports it and `PlanFailure.ownerMessage` supplies localized actionable guidance; `PlannerParser` distinguishes empty, non-JSON, broken JSON, truncation, invalid steps, excessive size and request failures and validates through `QueueParser`, so a plan can only use tools the requester may use), `tick/` (`GoalTickPolicy` decides when an idle companion with an unfinished goal is nudged; only `autonomous` may also ask what to do next), `autonomy/` (free time: `FreeTime` state per owner saved through the independent `FreeTimeRepository`; `AutonomyFacts` in, including a nested `SelfFacts` with own hunger, XP, gear wear, bed/table/anvil at home and portal materials, and `TradeRef` trade places; `NeedsAssessor` agenda out (at most six needs, reflex or director) covering self-care, base, ladder, farm, trade, enchanting and nether needs; `ProgressionLadder` (wood → stone → iron → diamond as data, with the missing gear item ids a fallback asks for); `ShiftPolicy` (once a second: reflex, director, fallback template or wait; an expired shift closes; `FALLBACK_ORDER` builds the base and storage before ladder stock; owner work, an active owner goal and the quiet period after the owner speaks come first), `ShiftBudget` (director shifts per hour online and offline, doubling backoff), `IdleStartPolicy`, `DefaultActivityPolicy` (the idle fallback follows the owner only when the follow mode is on and free time is not the companion's own business), `IdleWatchdog`, `ReflexPlans` (hunger, sleep, unload, shelter, farm creation, collect and the spent-budget fallbacks), `ShiftOutcome` (record, lesson, cooldown, new stage), `AwaySummary`, `FreeTimeStatus`/`FreeTimeText` (owner and model lines); at most two model requests per shift, and a failed shift is not replanned). Adapters: `server/agent/CompanionSessions` and its `PlannerAdapter`, its task-listener event adapter, `core/OutcomeFacts`, `server/agent/FreeTimeDriver` (free time on the server thread) and `AutonomyFactsBuilder` (world → `AutonomyFacts`, cached 5 s). Goal tools: `set_goal`, `update_goal`, `finish_goal` (OWNER only: a goal is replayed with the owner's authority).
- `engine/.../execution/queue/` — the plan queue behind `run_plan` and every goal: `Job`/`JobState`/`JobQueue`, `Guard`/`GuardAction`/`GuardFacts` (including boolean composition and world facts), `PlanNode`/`PlanDefinition`/`PlanCodec` (bounded conditional/repeat tree), `PlanCursor`/`PlanInterpreter` (deterministic, persisted control flow), `QueuePolicy` picks the next job, `QueueOptimizer`/`MergePolicy` collapse duplicates, `FailurePolicy` decides retries, `PlanRecord`/`PlanArchive`/`PlanStatus`, `QueueSave` (bounded queue snapshot JSON without an independent format prefix), `QueueSnapshot`/`QueueText` (menu rows and the planner view), `QueuedStep`, `QueueLimits`, `QueueNotice`, `PlanOptions`. Structured plans emit one leaf job at a time; the server refreshes `GuardFacts` at control boundaries and displays the bounded tree, selected path and repeat progress. `server/execution/tools/QueueTools` exposes `plan_help` and dry-run `plan_validate`; `ConditionalPlansTests` covers server-side branch, cap, hold, cancel and access-revocation behavior.
- `engine/.../features/combat/` — pure combat decisions: `ProtectionPolicy` (self only, bodyguard, guard, avoid combat), `FightingStyle`, `RetreatPreference`, immutable `CombatSettings` (persistence format and strict decode), `CombatMode`, `CombatSnapshot`/`CombatDecision`, deterministic `CombatPolicy` (priority, pursuit bound, target scoring, bounded lead aim), `ShieldPolicy` (raise on a draw or an arrow, lower to swing), `ThreatTable` (group score and stable selection), `GroupPressure` (sidestep away from a second threat), `WeaponPolicy` (tactical score, hysteresis band, bow swap band), `ProjectileThreat` (bounded segment/box intersection; deflection scoped out), `PotionFacts`/`PotionDecision`/`PotionPolicy`. Minecraft adapters: `features/combat/minecraft/CombatController` and `Threats`; task and tool contributors live in `features/combat/minecraft/`.

## Minecraft layer

## Runtime flows

### One chat or voice turn

1. A chat message reaches `ChatRouter.onChat`; voice text arrives as `VoiceTranscriptC2SPayload` and `VoiceTranscriptHandler` hops to the server thread. Trust confirmations are handled before addressing.
2. `AddressDetector` decides whether the companion is addressed; `CompanionRouting` → `CompanionPicker` chooses which companion hears it (own within hearing → nearest other within hearing whose owner is online). Nothing in range means no companion hears it and the sender is told it is too far.
3. `CompanionSessions.post` → `CompanionBrain.post`; guest throttling happens in `shouldDrop`.
4. `maybeStartTurn` batches the events for one principal, fixes `turnCaller`, appends one USER message and calls `requestStep`.
4a. The batch is routed (`TurnRouter`): the turn mode decides which tool groups are visible. A failed plan with replans left, and a complex request that sets a goal, consult the planner first; its plan is queued with the turn caller's access and shown once in the Mission block.
5. `requestStep` builds the system prompt with `PromptBuilder.system` and calls `gateway.complete(system, memory.snapshot(), tools.specs(access))`, where the specs are filtered to the visible groups when `agent.toolRouting` is on. Speech is still checked against every tool the caller has.
6. The response callback speaks the text and executes every tool call in order through `ToolRegistry.run`; tools normally start a `Task`.
7. Tool results are appended as TOOL messages and `requestStep` loops until there are no calls or `maxToolSteps` is reached; `endTurn` applies the cooldown.
8. When a task finishes, its `TaskListener` posts `TaskFinished` to the brain, which starts the next step.

### Task lifecycle

`QueueDriver` selects queued work and interprets plans; `ExecutionCoordinator` owns orders, scoped holds, suspension and default activity; `ActiveTaskController` owns the current or frozen task, captures its caller and settings snapshot, enforces timeout, and turns a thrown task callback into `FAILED`. Replacing a task calls `stop` once. If a task starts a replacement during its own tick, the old tick result is discarded after the replacement is installed. Terminal notifications pass through `TaskEventSink` and flush after the coordinator settles the transition, so listeners cannot reenter a half-finished queue update. With nothing to do the coordinator falls back to `FollowTask`, unless free time makes standing still the default (`DefaultActivityPolicy`, asked through `CompanionEntity.mayFollowOwner`). Pausing suspends ticking without losing the task: `CombatController` sets it around a retreat and around a fight it did not order, the companion inventory window owns an independent token, and so does the companion menu — `DebugStream.openMenu`/`closeMenu` owns a token and closes it on unsubscribe, disconnect, failed open and entity removal, so the world keeps ticking and only the companion pauses. Free time does not run behind the menu either: a held coordinator does not tick, and `IdleStartPolicy` already treats a paused runner as combat. `TaskPersistenceCoordinator` decodes the versioned execution document, attaches event listeners before notices, rebuilds only tasks known to the current registry, and rejects work whose actor or ephemeral spending authority is no longer valid.

### Death and respawn

`CompanionEntity.die` captures the body before the superclass death path: `CompanionEntity.saveCarry`
writes inventory, six equipment slots, hunger, XP, combat settings, pace and the bounded `SavedExecution`
document parts, `CompanionManager` adds the dimension, position, cause, killer and game tick, and
`CompanionCarryData` (world `SavedData` `friendai:companion_carry`) stores the body plus a capped
death log under the owner UUID. Furnace jobs and station leases are not saved by the entity; the
manager copies them in memory for a respawn in the same session. `dropCustomDeathLoot` does nothing:
the companion keeps what it carries, so there is no death loot and no duplicate.

`CompanionManager.tick` replaces the dead body after its unload callback, building the new entity
with the owner, the stored name, the skin store and the bed/shared spawn. It registers the entity,
drops any brain that still points at the dead body (`CompanionSessions.onEntityReplaced`, which bumps
the old generation), applies the saved body (`CompanionEntity.restoreCarry` → `readBody`, so the
queue, plan cursors and eligible task checkpoints restore through `TaskPersistenceCoordinator`) and clears the pending
body. Auto-respawn off and hardcore keep the record instead: the next `summon` applies it, and
`dismiss` clears it because dismissal already drops the inventory. A restored free-time plan keeps
its id and `free time: ` goal, so `FreeTimeDriver` reopens the shift; the driver ignores a
`isDeadOrDying()` body so a zero-health corpse cannot trigger a reflex that cancels it.

### Companion menu

The client subscribes with `CompanionRequestC2SPayload(SUBSCRIBE)`; `CompanionRequestHandler` calls `DebugStream.openMenu`, which subscribes the player, holds the owner's companion (`CompanionEntity.addMenuViewer`, so the work pauses while the world keeps running) and sends the first snapshot. `UNSUBSCRIBE` goes through `DebugStream.closeMenu`, the same path a disconnect and the ten-tick sweep take, and releases the hold. `DebugStream` pushes `CompanionSnapshotS2CPayload` every 10 ticks to subscribers; `SnapshotBuilder` builds it for the requester's own companion. A companion summoned, respawned or loaded while its owner's menu is open starts held (`CompanionManager.register`). Everyone sees status and task history; the brain log, prompt, perception text and tool names are operator-only (`DebugAccess`, checked on the server). The Memory tab sends `MEMORY_OPEN`/`MEMORY_CLOSE` and receives `MemoryViewS2CPayload`; the Places tab does the same with `PLACES_OPEN`/`PLACES_CLOSE` and `PlacesViewS2CPayload` (rename and delete travel as `PLACES_RENAME`/`PLACES_FORGET`).

### Instruction skills and self-teaching

`SkillService` captures the authenticated caller, current message/task, turn kinds, memory description/profile and the effective builtin/global/owner skill records before provider work starts. `CompanionBrain` captures one `SkillTurnSession` per turn; `CompanionSessions` enriches normal/free-time planner inputs through `PlannerAdapter`. Selection is explicit request, always-on, turn-kind match, then literal trigger, with ID tie breaks. Disabled/pending records never qualify. The instruction slice is at most `min(skills.promptBudget, agent.promptBudget / 5)` (2,400 characters by default, still capped when the agent budget is unlimited). Whole cuttable sections lose to mandatory rules. Final included IDs/character costs and provider token usage are operator diagnostics.

`use_skill` delivers an eligible explicit instruction once and displaces automatic guidance if needed. Accepted terminal goal transitions and finished shifts post a `SkillOutcome`; only that outcome turn offers `manage_skill`. The server rechecks owner/source/outcome/generation, six writes per rolling hour and two per outcome, persists the ledger, and requires owner approval for new model records by default. Cancel/dismiss/logout invalidate the brain context. Personal facts still use `remember` and the existing five categories. A skill cannot execute text or alter a tool's AccessLevel.

`SkillsViewStream` sends only the authenticated sender's paged catalogue and requested body. The Skills tab and the Description editor share bounded server actions with `/friendai skills ...` and `/friendai description ...`. Global writes require the separate operator command branch; they grant no access to other owners' books. Client saves carry request IDs so cached/unsolicited views cannot acknowledge a newer draft. Editor screens retain the menu subscription hold. Known configured secrets are checked again before prompts, views and exports; raw skill tool arguments/results are omitted from logs.

### Configuration

`ServerRuntimeFactory` builds the service graph for one `MinecraftServer`; the lifecycle registry removes it before idempotent close. `FriendaiServerState` loads `config/friendai-server.json` with `ConfigStore`; the client loads `config/friendai-client.json` the same way. `ConfigStore` writes atomically, keeps a `.bak` when it recovers from corruption, and runs versioned migrations. `ServerConfiguration` validates and resolves the config once, then publishes one immutable `ServerSettings` snapshot per server before notifying loaded task runners. Active tasks retain their start snapshot; tasks created after a reload use the new settings. `ServerConfig.activeProfile` → `toLlmProfile` → `LlmClient`; a reload rebuilds the client and registry-bound tools.

### Speech recognition

The client captures audio only while push-to-talk is held, resolves the selected provider (local Whisper or a cloud preset), checks readiness, transcribes on a daemon thread, and sends `VoiceTranscriptC2SPayload(text)` only if the server can receive it. The transcript hops to the client thread first. Local audio never leaves the machine; a cloud provider uploads the recording only while it is selected. The Whisper model is downloaded into `<gameDir>/friendai/models/` and verified by size and SHA-256.

### Speech output

`CompanionSpeaker` sends each reply as a `CompanionSpeechS2CPayload(companion, text, addressee, companionId, audibleRange)`, the last two filled from the speaking entity and `chat.hearingRadius`. The client's `SpeechRuntime` cleans and splits the text, then either synthesizes locally with sherpa-onnx (`client/audio/LocalTtsEngine`, a downloaded Piper voice) or calls a cloud engine (`infrastructure/speech/CloudTtsEngine`: OpenAI, ElevenLabs or Yandex) through `TtsClient` and `VoiceHttp` on a worker thread. `SpeechPlayback` plays the clip through the chosen device, opened with a small buffer so a change is heard without the device's default delay; when **Voice comes from the companion** is on (`voice.tts.spatial`), it mixes the clip to stereo in 20 ms blocks and ramps each channel from the previous block's gains to the `SpatialAudio` gains that `SpeechRuntime.tick` recomputes every client tick, so the pan and the attenuation follow the player without steps or clicks, and a reply whose companion is not in the client's level is dropped. With the setting off the clip plays centred at full volume. Synthesis is off by default; the settings live under `voice.tts` in the client config. `SpeechGate` drops a packet while recording or when it is addressed to another player and "speak for other players" is off. Push-to-talk and the **Stop speaking** keybind stop playback, and a late result is dropped by a generation counter. Only cloud engines send the reply text off the machine, keys travel in headers only, and paid requests are never retried automatically.

## Data and persistence

Owner-file persistence uses the pure `StoreCodec<T>` contract (including bounded `Reader` decoding) and
`StoreWriteStatus` with typed failure/read-only reasons. `OwnerFileStore<T>` lazily loads records and captures
immutable UTF-8 bytes plus their revision on the server thread. At most one snapshot per owner is pending;
a completion records only its own saved revision. A later server-thread flush captures any newer revision,
and final close repeats that capture/wait cycle until settled, failed, or its 30-second bound expires.
Normal `flushAll` and five-second debounce flushes never wait for disk. Queue rejection leaves records dirty
with `QUEUE_FULL`, allowing the next ordinary flush to retry. Status contains no paths, values or exception text.

`FriendaiServerState` acquires one bounded, single-thread `OwnerStoreWriter` through `RuntimeResources`
before acquiring stores. Memory, profiles, goals, free time, places, placements, knowledge, and both
instruction-skill scopes borrow it; reverse-order `ServerRuntime` teardown closes and flushes these stores
before closing the writer once. Standalone test stores may explicitly own a writer. Store close is idempotent
and never closes a borrowed writer.

Missing files stay absent until mutated. Corrupt files are backed up and remain read-only even when the backup
succeeds; failed backups and failed reads also preserve the original in read-only mode. Unsupported and oversized
files remain read-only. Atomic replacement falls back to replacement move only when atomic move is
unsupported. Before this non-atomic fallback, the writer preserves a separate recovery copy of an existing
target; failed replacement restores that target, and failed restoration retains the recovery copy. Successful
replacement/restoration removes the temporary recovery copy. Failed writes leave the latest revision dirty. The
package-local `OwnerFileOperations` seam makes backup, read, write and move failures deterministic in tests.
Domain wrappers accept an `OwnerFileStore.Factory` construction boundary, allowing their actual codecs and
owner/server scopes to run the same injected-failure contract without exposing file operations to features.

The companion inventory/equipment window uses a vanilla container menu (`menu/FriendaiMenus`), not a custom payload.

## Access and permissions

- `AccessLevel`: `GUEST < TRUSTED < OWNER`; each `Tool` has a minimum access, and `ToolRegistry.run` filters before execution.
- Memory rights: `AccessResolver` classifies the caller; `MemoryPolicy` decides read/write/forget per subject; a guest only sees facts about themself. Trust changes need the owner's confirmation (`TrustConfirmations`).
- Operator-only: brain log, prompt, perception text and debug tools (`net/Operators`, `debug/DebugAccess`); `/friendai reload` requires gamemasters.
- The movement debug stream (`net/MovementDebugStream`) combines the active task's on-demand work snapshot with independent route obstacle cells. Its append-only optional codec section preserves true per-status counts when cells are capped; the client renders only nearby/in-front work cells and keeps the default-off preference in `friendai-client.json`.
- Owner-only: instruction skill CRUD, approval, description and owner profile. The sender selects their own book; no payload selects an owner UUID. Custom instructions/profile details never enter guest/trusted prompts.
- Owner-only: the companion inventory window (owner, same dimension, within 8 blocks, alive).
- World protection: `CompanionHands.canInteract` asks `level.mayInteract` through a fake player; build/break blacklists come from `ServerConfig` (the owning server's `ServerSettings` snapshot and pathing blacklists).


Planner-only gateway calls use completeJson: the optional request flag emits JSON mode for OpenAI Chat/Responses, Gemini and Ollama; Anthropic and custom gateways retain prompt-only behavior. Ordinary brain turns keep prose/tool output. Planner attempt events and queue dispositions use the operator-only PLANNER log kind with bounded redacted replies; owner status and menu diagnostics show the effective planner model. Config schema 15 adds total planner attempts and validates profile selection; schema 16 adds the free-time watchdog timeout.
