# ARCHITECTURE.md

The reference half of the project guide: what each source set and package is for, how one chat turn and one task run, what is persisted where, what crosses the network, and who may do what. Read it before changing a package you have not worked in.

`AGENTS.md` is the other half and the one every session loads: commands, workflow, testing, git hygiene, versioning. When a file here disagrees with the code, the code wins — fix the stale file in the same commit.

## Source sets

The root Gradle project remains the Loom mod and uses `loom.splitEnvironmentSourceSets()`; one mod (`friendai`) spans `main` + `client`. The included `:engine` Java library is compiled separately and embedded once in the distributed mod jar. Engine owns foundation text/diagnostics/limits/persistence contracts, execution queue/tool contracts, agent turn/planning/prompt/routing and LLM model/protocol/provider logic, game-independent feature policies including speech, and JVM configuration, speech HTTP/model-download, appearance HTTP and persistence adapters. Native speech engines and client audio remain in root/client.

| Source set | Path | Contains | Notes |
|---|---|---|---|
| `engine main` | `engine/src/main/java` | Foundation and persistence contracts, execution, agent and feature policies, JVM config and persistence adapters | No Minecraft, Fabric, optional UI or native audio compile dependency. |
| `engine test` | `engine/src/test/java` | Pure unit tests | Root `test` aggregates `:engine:test`. |
| `engine testFixtures` | `engine/src/testFixtures/java` | Reusable pure fakes | Never included in the shipped mod jar. |
| `main` | `src/main/java` | Pure layers, Minecraft-layer server/common code, resources | The shipped jar's common half. |
| `client` | `src/client/java` | Renderer, screens, HUD, keybinds, voice capture, speech output | Loaded only on the client. |
| `test` | `src/test/java` | JUnit tests and reusable fakes | No Minecraft at runtime. |
| `gametest` | `src/gametest/java` | Fabric GameTest classes plus `GameTestSupport` | Separate mod `friendai-gametest`; entrypoints listed in `src/gametest/resources/fabric.mod.json`. CI's shard map is `.github/gametest-shards.json` and `scripts/run-gametest-shard.sh` boots one class per server. |

## Overview

Bottom-up. The dependency rule is per class/module, not per package: **engine classes must not import `net.minecraft.*`, `net.fabricmc.*`, optional UI libraries or native audio bindings**. `server/agent/chat/`, `server/agent/perception/`, `server/net/` and `perception/resource/` are Minecraft-facing adapters; `agent/perception/` holds pure perception views. `transport/` adapts typed engine protocol values to Fabric payloads. JVM adapters live in `infrastructure/`; feature packages depend on ports and foundation contracts, never on infrastructure implementations.

```
root Fabric mod  (server/entity, client source set, bootstrap and adapters)
   |  depends on the game-independent module and embeds it in the mod jar
engine  (foundation, execution contracts, agent, pure feature policies, presentation, JVM infrastructure and LLM protocols)
```

Cross-feature dependencies are explicit and directed, and `PackageDependencyRules` enforces every dependency with positive and negative fixture coverage: social reads an owner's own durable statements out of memory, and the reverse `memory` → `social` edge is the bond. `foundation/` and `world/` are the shared kernel: a pure policy two features need lives in `foundation`, a Minecraft helper two features need lives in `world`, and neither kernel layer may name a feature, an adapter or a runtime package. Navigation drives live digging and bridge-material gathering through the kernel's block-breaking and `MaterialGatherer`; mining uses the kernel's `PathSearch` and `PathExecutor`. Acquisition may call creative capability operations, but it cannot construct creative task implementations. Interaction consumes the creative command policy, combat threat checks, and the kernel's public entity-movement and target APIs; navigation does not construct interaction tasks. Inventory reuses acquisition's tool-requirement data, kernel target/movement APIs, remembered-place queries, and the pure hunger model; container opening and item transfer mechanics are shared through `task/interact/ContainerSession` and `ContainerTransfer`. Animals uses combat threat facts, the kernel block matcher and navigation approaches; combat uses the kernel equipment helpers, navigation and the pure hunger model; construction uses fire hands for safe clearing; survival composes combat threats, cooking, farming, knowledge observations, mining and navigation support; fire uses crafting, mining and navigation adapters. Feature Minecraft tool adapters may depend on exactly `server/execution/tools/FeatureToolContributor`, `FeatureToolRegistry`, `TaskToolDefinition`, and the nested `TaskToolDefinition.Factory`, `TaskToolDefinition.CallerFactory`, and `TaskToolDefinition.QueueTraits` helpers to register contributions; server runtime services remain outside the feature boundary.

The feature graph is acyclic with no baseline file: a cycle between two feature packages is fixed by moving the shared part into the kernel or turning one side into a port, not by recording an exception. `FeatureGraph` computes strongly connected components over class-level edges and fails the build on any component larger than one package.

## Pure Java modules

- `engine/.../agent/llm/model/` — `Message`, `ToolCall`, `LlmRequest`/`LlmResponse`, `LlmException`. Invariant: a malformed tool-argument JSON leaves `ToolCall.arguments == null` while `rawArguments` is kept; Gemini's opaque `signature` must be echoed back.
- `engine/.../agent/llm/protocol/` — one class per wire format: `OpenAiChatProtocol`, `OpenAiResponsesProtocol`, `AnthropicMessagesProtocol`, `GeminiProtocol`, `OllamaProtocol`; each has `toWire`/`fromWire` and calls the `JsonHttpTransport` port. Anthropic and Gemini must receive consecutive USER/TOOL messages as **one** user message; malformed arguments serialize as `{}`.
- `engine/.../agent/llm/provider/` — presets and routing as **data**: `ProviderPreset`, `RoutingRule`, `Route`, `LlmProfile`. First glob match wins; base URL precedence is profile → rule → preset. Protocols and presets are registered in `ProviderRegistry.withBuiltins`.
- `engine/.../protocol/` — the pure version-1 companion wire contract: explicit family/operation IDs, bounded frame and bootstrap codecs, request sequencing, capability negotiation, pure handshake session state, typed C2S requests and framed control/memory/places/instructions/trading/debug/speech views. It contains no Fabric or Minecraft classes. Root adapters are in `transport/`, `server/net/` and `client/net/`.
- Root `llm/http/HttpTransport` implements the engine JSON transport port and retains retries only for retryable error kinds, HTTP-status mapping and key redaction; root `llm/LlmClient.complete` resolves the route and delegates.
- `infrastructure/config/` — `ConfigStores` composes production stores with `ConfigMigration` adjacent steps and validators. `ConfigStore` limits reads/writes to 8 MiB, validates upgrades before I/O, preserves unknown fields through later saves, makes unique byte-exact `.v<source>.<unique-id>.bak` backups and requires atomic replacement. `ConfigFileOperations` is the package-local disk seam; `ConfigJson` preserves extension fields in objects and arrays, matches reordered entries, and refuses ambiguous edits with unmatched extension data. Failed upgrades/read/backup/replacement leave originals read-only and use defaults in memory; reload retries. Unknown, missing and future schema versions remain unsupported and untouched. Corruption recovery retains a separate `.bak` and never logs parser contents. `ServerConfig` and `ClientConfig` hold defaults and validation, and the chain's tests are the source of truth for which older versions still upgrade; `VoiceDraft`, `VoiceConfig`, `SecretResolver` (`env:NAME`) support editing. A key typed into a config is stored there in plaintext, so `env:NAME` is preferred; keys are never logged, put in a URL, or included in toasts and error messages, and the settings screen masks them until **Show key** is pressed.
- `engine/.../foundation/text/` — `UserMessage(key, args)` and `UserFacingException`: the only player-facing protocol flowing out of pure layers; `LanguageDetector` (script counts plus a few stopwords, quoted spans and `/commands` ignored) and `LanguageMemory` (commits the first confident sample, switches only after three in a row) learn the owner's language. `foundation/session/ClientSessionId` names one client connection, so a callback queued by an older connection can be rejected.
- `engine/.../execution/tool/` — `Tool`, `ToolRegistry`, `ArgValidator`, `SchemaBuilder`, `AccessLevel`/`Caller`, `PlanParser`, `InventoryAccess`, `StopScope`. `ToolRegistry.run` never throws: unknown/disabled tool, wrong access, bad JSON or schema violation become `ToolResult.error`. A documented argument alias is applied everywhere a call is parsed — a direct tool call, a plan step and a `queue_edit` — so the same call means the same thing on every path. Access is ordinal `GUEST < TRUSTED < OWNER`; the default minimum is `TRUSTED`. Gameplay contributors live with their feature; the ordered server bootstrap is `server/agent/tools/FriendaiTools`.
- `engine/.../agent/turn/` — `CompanionBrain` (the agent loop, one principal per turn), `PromptBuilder`, `ConversationMemory`, `AccessResolver`, `BrainEvent`, `AgentSettings`, and the ports the agent layer plugs into the loop: `GoalSource` (the goal shown in the prompt) and `PlannerPort` (consult the planner, queue its plan). `SkillTurnSession` is the boundary to the root instructions adapter. Invariants: at most one LLM request in flight per turn; a generation counter silently drops late responses, including a planner proposal that arrives after a stop; trimming drops whole leading USER turns so history never starts with a tool result. A successful `queue_add` with no failed calls or other queue mutation ends the turn when a reply survives ReplyGuard, or silently when an event-only recovery queued a replacement; a batch containing a player message still needs an answer. The planner is consulted at most once per turn, before the first model request; setting a goal or failing a `queue_add` never triggers a second consultation. `BrainObserver` is the passive hook; `onReply` reports the text a player actually heard, `BrainObservers` fans one event out to the debug log and the transcript, and `LogActions` serves `read_log`.
- `agent/routine/` — the owner-defined recurring timetable: `Routine` (one routine, phase/interval trigger, 1–8 flat steps, run cap, durable occurrence state), `RoutineSchedule` (game-tick next-occurrence, due, missed-window and advance math with no wall clock), `RoutineSave` (bounded payload) and `RoutineRepository`. A routine is one ordinary queue plan; there is no second scheduler.
- `agent/` — the cognitive layer above the task queue, all pure Java. `turn/StreamSpeechPolicy` keeps an early-speech prefix conservative until the full-response guard completes. `coordination/` derives cross-companion claims from live queue jobs (`CompanionClaim`) and keeps bounded, expiring help requests (`HelpRequest`/`HelpRequestBook`) that grant only the named help, and bounded handoff offers (`HandoffRequest`/`HandoffBook`) naming one item, quantity and meeting point; acceptance revalidates both companions, both owners and the source count before moving the exact quantity once, and a consumed offer cannot replay. `autonomy/` (`ShiftContract` states each free-time shift's purpose, budget and closed `ShiftStopWhen`; `WorkConflict` refuses autonomous work that duplicates a live job or an owner order; `ShiftBlocker` keys a failure by its cause so a repeated blocker is reported once; `FreeTimeLogEvents` builds the durable `shift.start`, `shift.end` and `shift.report` records). `goal/` (`GoalBoard`: one primary and up to three background goals with criteria that may carry a queue `Guard`, at most five 160-character lessons, a replan budget, and an optional deadline tick shown in the prompt as due or overdue; `GoalSave` encodes the target JSON payload; `GoalService` uses the independent owner `GoalRepository`, so goals outlive the entity), `route/` (`TurnRouter` picks chat, action, goal, recovery or event from deterministic English and Russian vocabularies in `agent/intents_*.json`, defaulting to action with every tool group; `RouteSignals` and `PlanSignals` feed `PlanningPolicy`, which names a `PlanSubject` — owner order, unmet active goal, troubled plan or free-time shift — when the occasion deserves a plan, before the first model request, under `PlannerMode` (`auto` by default, `off`, `always`)), `tools/` (`ToolCatalog`: every tool belongs to a `ToolGroup` and may carry a "when to use" hint; core tools are always visible, `request_tools` unlocks a group for the turn; `plan_validate` belongs to the `PLANNING` group and is unlocked with `request_tools`, so a turn whose visible groups are restricted (a chat or goal turn) does not advertise it, while the unclear-order fallback that grants every group still does; a tool missing from the catalog is always visible, and a GameTest fails the build until every registered tool has an entry), `prompt/` (`PromptSection`, `PromptAssembler` with a character budget that cuts tool hints first, then rules, memory, mission and state, and never identity, speech, working method or role; `DefaultSections`, `MissionText`), `verify/` (`OutcomeChecker` turns before/after `WorldSnapshot`s into at most eight facts), `recover/` (`RecoveryAdvisor` classifies a failure text and suggests remedies not yet tried; `FailureHandler` appends facts and diagnosis to events and spends the goal's replan budget), `plan/` (`Planner`, `PlannerObjective` (what one subject asks for, as prompt data), `PlannerInput`/`PlannerPrompt`, `PlanSubject` (the sealed set of planning occasions), `PlannerScope` (which tool names one occasion may plan with: the whole plannable set, except that a repair keeps only the groups its plan's steps belong to), `LlmPlanner` drafts one plan in one provider call, optionally in native JSON mode, with the per-call timeout (`agent.plannerTimeoutSec`, default 20 s) and at most `agent.plannerRetries` total send attempts (1–4, default 2), where a transport fault inside one attempt is still retried by the HTTP layer; a rejected reply is final and is returned to the model's tool loop instead of being re-sent, and a cancelled turn sends nothing further; `PlanAuthority` decides whether the failed or next-pending job's principal still holds every step's access, and `ReplanBudget` bounds goal-less repairs; `PlanFailure` carries a code, bounded diagnostic and attempt, `PlannerException` transports it and `PlanFailure.ownerMessage` supplies localized actionable guidance; `PlannerParser` distinguishes empty, non-JSON, broken JSON, truncation, invalid steps, excessive size and request failures and validates through `QueueParser`, so a plan can only use tools the requester may use; `PlanPatchPolicy.reject`/`rejectPlan` name what an edit may touch — a flat pending or failed step, or a structured tree that never started — and are the one rule both the preflight and the patch apply), `tick/` (`GoalTickPolicy` decides when an idle companion with an unfinished goal is nudged; only `autonomous` may also ask what to do next), `autonomy/` (free time: `FreeTime` state per owner saved through the independent `FreeTimeRepository`; `AutonomyFacts` in, including a nested `SelfFacts` with own hunger, XP, gear wear, bed/table/anvil at home and portal materials, and `TradeRef` trade places; `NeedsAssessor` agenda out (at most six needs, reflex or director) covering self-care, base, ladder, farm, trade, enchanting and nether needs; `ProgressionLadder` (wood → stone → iron → diamond as data, with the missing gear item ids a fallback asks for); `ShiftPolicy` (once a second: reflex, director, fallback template or wait; an expired shift closes; `FALLBACK_ORDER` builds the base and storage before ladder stock; owner work, an active owner goal and the quiet period after the owner speaks come first), `ShiftBudget` (director shifts per hour online and offline, doubling backoff), `IdleStartPolicy`, `DefaultActivityPolicy` (the idle fallback follows the owner only when the follow mode is on and free time is not the companion's own business), `IdleWatchdog`, `ReflexPlans` (hunger, sleep, unload, shelter, farm creation, collect and the spent-budget fallbacks), `ShiftOutcome` (record, lesson, cooldown, new stage), `AwaySummary`, `FreeTimeStatus`/`FreeTimeText` (owner and model lines); at most two model requests per shift, and a failed shift is not replanned). Adapters: `server/agent/CompanionSessions` and its `PlannerAdapter`, its task-listener event adapter, `core/OutcomeFacts`, `server/agent/FreeTimeDriver` (free time on the server thread) and `AutonomyFactsBuilder` (world → `AutonomyFacts`, cached 5 s). Goal tools: `set_goal`, `update_goal`, `finish_goal` (OWNER only: a goal is replayed with the owner's authority).
- `engine/.../execution/queue/` — the plan queue behind `run_plan` and every goal: `Job`/`JobState`/`JobQueue`, `Guard`/`GuardAction`/`GuardFacts` (including boolean composition and world facts), `PlanNode`/`PlanDefinition`/`PlanCodec` (bounded conditional/repeat tree), `PlanCursor`/`PlanInterpreter` (deterministic, persisted control flow), `QueuePolicy` picks the next job, `QueueOptimizer`/`MergePolicy` collapse duplicates, `FailurePolicy` decides retries, `PlanRecord`/`PlanArchive`/`PlanStatus`, `QueueSave` (bounded queue snapshot JSON without an independent format prefix), `QueueSnapshot`/`QueueText` (menu rows, the planner view, `finishedSummary` for a plan's terminal step results and the archived-plan lines `queue_show` renders), `QueuedStep`, `QueueLimits`, `QueueNotice`, `PlanOptions`, and `PlanMaterials` (what the remaining steps still need, by item id: obtaining, crafting and smelting name an item, mining names a block and reserves what it yields). Structured plans emit one leaf job at a time; the server refreshes `GuardFacts` at control boundaries and displays the bounded tree, selected path and repeat progress. `server/execution/tools/QueueTools` exposes `plan_help` and dry-run `plan_validate`; `ConditionalPlansTests` covers server-side branch, cap, hold, cancel and access-revocation behavior.
- `engine/.../features/inventory/` — pure inventory policies that need no world: `DeliveredLedger` (the bounded newest-32 hand-overs the companion performed itself, each with the drop entity that carries it and a 600-tick window, so a `delivered` criterion can be evidenced by the drop while it exists and returns to unproven once it is gone).
- `engine/.../features/storage/` — pure query model over observations the knowledge store already records: `StorageKey`, `ContainerRecord` (counts, slots, kind, last-seen tick), bounded `StorageIndex` (eviction, freshness, kind truncation) and `StorageTargets` (take/store/deposit ordering, distance and freshness), plus `StorageText`. No world reads: an unopened container is unknown, and "no record" is never "absent".
- `engine/.../features/combat/` — pure combat decisions: `ProtectionPolicy` (self only, bodyguard, guard, avoid combat), `FightingStyle`, `RetreatPreference`, immutable `CombatSettings` (persistence format and strict decode), `CombatSnapshot`/`CombatDecision`, deterministic `CombatPolicy` (priority, pursuit bound, target scoring, bounded lead aim), `ShieldPolicy` (raise on a draw or an arrow, lower to swing), `ThreatTable` (group score and stable selection), `ThreatClass`/`ThreatRules` (hostile, provoked-only, avoid, ignore; warden/dragon and piglin-group rules), `GroupPressure` (sidestep away from a second threat), `WeaponPolicy` (tactical score, hysteresis band, bow swap band), `ProjectileThreat` (bounded segment/box intersection; deflection scoped out), `PotionFacts`/`PotionDecision`/`PotionPolicy`. Minecraft adapters: `features/combat/minecraft/CombatController` and `Threats`; task and tool contributors live in `features/combat/minecraft/`.
- `engine/.../features/creative/` — the creative ruleset as data: `CreativeMode`, `CreativeAction`, `CreativeActionContext` (initiator + mode revision), `CreativePermissions`, `CreativePolicy`, `CreativeCommandPolicy` (the command allowlist), `CreativeItemCount` (bounded arithmetic for item requests). Server adapter: `server/creative/CreativeModeService`.
- `features/crafting/` — pure recipes, station policy and planning: `Recipe`, `Ingredient`, `Station`, `RecipeBook`, `CraftPlanner` (depth ≤ 5; `plan` for one target, `materialsFor(targets, …)` for the summed raw need of a whole target set with each need's candidate ids; selected batch branches share carried materials and one reusable station), `CraftPlan`, `CraftStep`, `StationLease` (600-tick lease, opaque packed position), `CraftText`, `StationPolicy`, `StationFallback` (one batch pass decides `Next`, `Blocked` or `Done` when a station is neither nearby, carried nor craftable from obtainable materials, so the pass tries the next recipe route or names the shortfall). Minecraft adapters: `features/crafting/minecraft/RecipeIndex`, `Stations`, `task/CraftTask`, and the `CraftingTools` contributor.
- `features/acquisition/` — acquisition planning: `ObtainPlanner` (inventory → containers → craft/smelt/mine/hunt/harvest/shear/milk/explore, depth ≤ 8), `ObtainStep` (sealed; 9 kinds), `Source`/`SourceBook`, `WorldFacts`, `OreDepths`, `ToolKind`/`ToolNeed`, `ObtainText`. A mineable target whose block is nearby, or whose exploration is allowed, is mined instead of being crafted, so a recipe that would need a station the companion does not have never blocks the obvious mine; a craft whose station is already usable here keeps its route. `Tier` is shared pure data in `engine/.../foundation/item/`. Adapters: `features/acquisition/minecraft/search/`, `task/ObtainTask`, `task/BatchObtainTask` (one shared raw-material demand for a target set, satisfied through `ObtainTask`, then each target crafted through the existing craft task), `SearchResourceTask`, `VisitResourceTask`, and the `ObtainTools` contributor (`obtain_item`, `obtain_items`, `plan_obtain`); `ResourceSearchTaskFactory` is its composition port, and `MinecraftObtainSubtaskFactory` turns a log `ObtainStep.Mine` into a whole-tree `FellLogsTask` (tree search, feller, a top-up pass, and the count miner for loose logs and creative). A visit that ends `ABSENT` or `OCCLUDED` forgets the site's checked members (`ResourceCandidates.confirmAbsent`), so the next plan does not tour an empty place again.
- `engine/.../foundation/spatial/` — pure block-grid A* and shared geometry: `PathSearch` (incremental, per-tick time budget, resumable), `MoveGenerator` (walk/fall/swim/climb/dig/pillar/bridge, a rising water stroke does not spend the lateral under-water budget, plus the jump over a gap, sized by `LeapPhysics`: up to three empty cells on the flat, fewer when landing a block higher, up to four when landing lower; a body that cannot sprint is only offered the one-cell hop), `Cell`/`CellView`/`Node`/`Pos` (packed keys; a cell carries the height of its standable top, so a climb from a slab, a carpet or a snow layer is measured by the real rise and an impossible one is never planned), `CostModel`, `GoalPoint`/`GoalReach`/`GoalPickup` (the pickup volume: body box inflated by the reach against the item box, so a drop in a pit is a goal from the rim), `LineOfSight`, `BlockList`, `MaterialPrices`, `MaterialReserve` (what the planned work still needs, per item, consulted before any block is spent), `PathingConfig`, `PathPolicy`, `BreakProgress` (each goal also names itself and the cells the overlay draws, so no caller switches on its type), `PathSmoother` (collinear plain runs collapsed into one leg), `RelativeDirection`, and `Path`'s complete-passage rule: `passagePrefix` cuts a partial route at its first placement, so a stair or bridge the companion cannot finish is never walked half-built. Minecraft adapters: `world/movement/LevelCellView`, `Navigator`, `PathExecutor`, `MaterialGatherer`, and movement task implementations. Named-place-relative resolution lives in `world/targeting/NearResolver`.
- `engine/.../foundation/movement/` — movement policy and orders: `ArrivalPolicy`, `Emotes`, `BodyFacing`/`Facing` (the single body-orientation policy: one claim from an action or travel, bounded yaw/pitch turns and settled-aim hysteresis), `FlightSearch`, `MovementOrders`, `PathSteering` (bounded turn and heading held through a climb or descent), `PacePolicy` and `PaceMode`. ## Minecraft layer

- `mixin/` — the mixin set declared in `friendai.mixins.json` with `defaultRequire: 1`: `PiglinAiInvoker`, `BehaviorUtilsBarterOutputMixin`, `NearestAttackableTargetGoalMixin` (vanilla hostile goals ask for `Player`, so after the vanilla search it also considers a `CompanionEntity` under the same conditions and prefers the nearer one), `TargetGoalAccessor`, and `PlayerAdvancementsMixin` (feeds the happenings journal because Fabric has no advancement event).
- `server/runtime/` — `ServerRuntime` owns one server's lifecycle and delegates event work; package-private `ServerServiceGraph` composes its domain services, `ServerRuntimeFactory` closes partial graphs, `RuntimeResources` closes owned actions in reverse order and continues after failures, `ServerTickPipeline` preserves tick order, and `OwnerRecordFlush` submits due profile, goal and free-time snapshots on the server tick using their stores' five-second cadence. `ServerRuntimeRegistry` is a narrow bridge for Fabric boundary callbacks; event adapters that receive only a player/server may use `find` and never create a runtime. `SERVER_STOPPING` stops new work and releases tickets/trade sessions; `SERVER_STOPPED` closes stores through the runtime resource stack.
- `server/execution/` — `ActiveTaskController` owns the active and frozen task lifecycle, timeout accounting, a per-task `ProgressWatch` stall check, task-start snapshots and crash isolation (a thrown tick becomes `task crashed: <Class>: <redacted message>`, and the stack stays in the server log); `TaskStartContext` captures the actual caller and creative authority, `StopRequest` records stop intent, and `TaskEventSink` is the shared notification boundary. `TaskEventDispatcher` publishes the settled events so a listener cannot reenter a half-applied queue transition, and `RunnerMetricsView` is the read-only progress and loop-metrics view the runner reports through. `engine/.../task/TaskPhase`, `TaskProgress` and `TaskProgressThrottle` define the structured lifecycle reported through `TaskEventSink.onDiagnostic`, `TaskLogCorrelation` and the existing log pipeline without a model turn. The runner captures full detail lazily for immediate waiting/running transitions, material-progress records at most every 100 active ticks, and unchanged/waiting samples every 200 active ticks; held or frozen ticks do not advance those intervals. Periodic samples use `task.progress`; only pre-stall capture uses `task.snapshot`. `clock.gap` snapshots the current activation (otherwise frozen), full status and execution context before resumed work, retains an unknown reason, and stays detached when idle. `ExecutionCoordinator` owns orders, scoped holds, suspension and default activity; `QueueDriver` selects jobs, advances conditional plans, handles guarded results and resolves factories; `QueueMutationService` runs every cancel, skip and clear operation inside one coordinator transition, so an outside party cannot stop or drop work in the middle of a queue update. Before a job starts, the coordinator asks its `StepFactory.authorized` (or the structured `PlanStepFactory.authorized`) whether the principal still holds the tool's minimum access — direct, flat-plan, structured and restored jobs share that one boundary — and a refusal cancels the job with the revocation reason instead of running it.

## Runtime flows

### One chat or voice turn

1. A chat message reaches `ChatRouter.onChat`; voice text arrives in a typed SPEECH-family `ProtocolRequestC2SPayload` and `ProtocolRequestDispatcher` invokes `VoiceTranscriptHandler` on the server thread. Trust confirmations are handled before addressing.
2. `CompanionRouting.route` runs `CompanionPicker.pick` first, because the name that counts is the recipient's (own within hearing → the nearest other within hearing whose owner is online); `AddressDetector` is then built with that name. An addressed line with no recipient is answered `friendai.companion.too_far` only when the sender owns a companion; an unaddressed line reaches only the sender's own companion, and only with `chat.listenAll`.
3. `CompanionSessions.post` → `CompanionBrain.post`; guest throttling happens in `shouldDrop`.

   A reply streams when the profile's protocol implements `StreamingProtocol` (OpenAI-compatible chat today) and the
   gateway has a `StreamingHttpTransport`: `LlmClient.completeStreaming` sends the ordinary body with the provider's
   stream flag, `SseFrames` decodes the body into frames, the protocol turns each frame into text deltas and tool-call
   fragments, and `StreamAssembly` builds the authoritative `LlmResponse` — text and complete tool calls — that the turn
   uses. Deltas are advisory speech only. A profile that cannot stream, a transport failure before the first delta, or a
   body that produced nothing falls back to one ordinary `complete` request, so every provider behaves as before. Once a
   delta has been delivered the stream is the answer: a body that ends without the provider's terminal frame
   (`finish_reason` or `[DONE]`) fails as incomplete rather than passing a partial reply or its half-assembled tool
   calls on, and cancelling the returned future cancels the body and starts no fallback.
4. `maybeStartTurn` batches the events for one principal, fixes `turnCaller`, appends one USER message and calls `requestStep`.
4a. The batch is routed (`TurnRouter` → `RouteDecision`): the turn mode decides which tool groups are visible, and `PlanningPolicy` names a `PlanSubject` when the occasion deserves a plan — an owner line that asks for a plan, spans several kinds of work or carries a complex marker; a failed or blocked plan with replans left whose principal still holds every step's access (`PlanAuthority`); an unmet active goal with no queued work; a free-time shift. A troubled-plan subject is preflighted with `PlanPatchPolicy.rejectPlan`, the same rule the patch later enforces: a plan whose interpreter frame cannot be rewritten, or whose steps are all finished, costs no provider call and no replan attempt. The model receives the refusal reason and guidance for repairing the existing queue with `queue_edit`. Greetings use the chat route, and known task and block events start with their tool group and the shared recovery groups. If an execution failure arrives during a request for the same principal, the next request includes the new outcome before applying a reply or tool call. The subject goes through `PlannerInputFactory` (world facts, the tools the caller may use, the failure text) to `PlannerPort.propose`; the answer is queued with the turn caller's access through `PlannerPort.apply` and shown once in the Mission block. A failed proposal falls back to the model with a note, and a blocked structured plan says how much work still stands (`PlanInterpreter.Remaining`; a lower bound when a guard cannot be decided). The consultation happens once, before the first model request, and never after a step; `PlannerScope` narrows a repair to the tool groups its plan's steps belong to, while every other subject keeps the whole plannable set. `agent.plannerMode` decides how eagerly this happens: `auto` uses the rules above, `off` never asks the planner about any subject — owner order, unmet goal, troubled plan or free-time shift, which then takes its deterministic fallback — and `always` asks about every actionable owner order, one that names recognized work, a complex marker or a plan request (for diagnosis).
5. `requestStep` builds the system prompt with `PromptBuilder.system` and calls `gateway.complete(system, memory.snapshot(), sent)`: `sent` is `tools.specs(caller access)` minus `manage_skill` outside a teaching turn, filtered by `ToolCatalog` to the visible groups (or every group when `agent.toolRouting` is off), with `trade_item` hidden on a `CHAT` turn. `turnToolNames` keeps every caller-visible name, so `ReplyGuard` hides any of them from speech.
6. The response callback offers the reply to `ReplyGuard` (which may reduce it to silence) and executes every tool call in order through the bound `ToolExecutor` (`ToolRegistry.bind(...).execute`); a task tool starts a `Task` or queues a `QueuedStep`.
7. Tool results are appended as TOOL messages and `requestStep` loops until there are no calls, `maxToolSteps` is reached, or the response queued a plan and answered the owner; `endTurn` applies the cooldown.
8. The owner's own hold (`/friendai pause`) is `ExecutionCoordinator.setManualPause`: it suspends the runner without
   dropping the active task, survives a rejoin or respawn because `resume` keeps `suspended = manualPause`, and
   releases with `resume`. A task under the hold is never reported as finished.
9. When a task finishes, `TaskEventSink` posts `TaskFinished` to the brain with the plan and goal it belonged to
   (`onFinished(id, planId, tool, status, summary)`, the four-argument form still supported for listeners that do not
   care), so the prompt line reads `task #N ... (plan #P) (goal #G)` and the next turn can connect the result to the
   goal it was meant to prove.

### One owner request: who decides, and what each hand-off must keep

The chain below is one request from chat to speech; a change may alter a step's policy but not the contract at its hand-off.

1. `ChatRouter.onChat` — decides whether a line is a request. Contract: it consumes a trust answer, lets `LocalOrderExecutor` run a recognized order through the registry instead of the brain, and posts at most one `BrainEvent.PlayerSaid` per accepted line. It must not pick a recipient or post twice.
2. `CompanionRouting.route` → `CompanionPicker.pick` — decides who hears it. Contract: a pure pick, the sender's own companion within `chat.hearingRadius` first, then the nearest other companion within it whose owner is online when guests are enabled. It must not consult perception or answer for a companion that cannot hear the line.
3. `CompanionSessions.post` → `CompanionBrain.post` — decides acceptance. Contract: `shouldDrop` is the only filter and it throttles guests alone (cooldown, `MAX_PENDING_PER_GUEST`); every drop is observed, never spoken. It must not run a turn on the caller's thread or drop an owner event.
4. `CompanionBrain.maybeStartTurn` — decides the turn. Contract: one principal's batch, the turn's `generation` captured at start, `thinking` set before any request, `turnCaller` fixed for the turn, `visibleGroups` reset from `RouteDecision`. It must not start a turn while one is in flight or reuse another principal's history.
5. `TurnRouter.route` — decides mode and groups without a model call. Contract: unclear text degrades to `ACTION` with every group, never to less capability; the planner is asked by `PlanningPolicy.beforeTurn(signals, plannerMode)` under `agent.plannerMode`; only an explicit owner trading verb mints a spend scope. It must not derive authority from a topic or a queued result.
6. `CompanionBrain.requestStep` — decides what the model sees. Contract: `PromptBuilder.system`, `memory.snapshot()`, and catalog-filtered specs (`trade_item` hidden in `CHAT`) with one request in flight. It must not send a schema the caller cannot use or run a tool before the response.
7. `CompanionBrain.onResponse` — decides what is said and run. Contract: `ReplyGuard` may reduce the text to silence but never drops a tool call; calls run in order, each appending exactly one TOOL message, errors included. It must not act on a stale `generation`.
8. `GoalTools`, `QueueTools`, `TaskToolRuntime.tool` — decide what work exists. Contract: goals are OWNER-only and saved through `GoalService`; `queue_add` validates against the caller's allowlist and links a plan to a planless goal; a task tool starts a `Task` or enqueues a `QueuedStep` and reports `task #N` / `job #N`. They must not save an `AccessLevel`: `CompanionSessions.currentCaller` re-resolves it at activation.
9. `ExecutionCoordinator.tick` → `QueueDriver` → `ActiveTaskController` — decides what runs. Contract: priority then queue order among ready jobs (`SKIP` guards skipped first), one active task, a direct task freezes a queue job, and `ActiveTaskController` turns timeout, stall and a thrown tick into `FAILED`. It must not start work under a hold.
10. `ExecutionCoordinator.emit` → `TaskEventSink` — decides when it is published. Contract: `emit` defers events to `pendingEvents` during a transition and flushes after it settles; `CompanionSessions` posts only for the current session and companion, adding the plan and goal correlation. It must not let a listener reenter a half-settled queue update.
11. `SessionEvents.extra` → `OutcomeChecker` / `FailureHandler` — decides whether the result is proven. Contract: `OutcomeChecker.check` compares the before/after `WorldSnapshot` with the goal's criteria and can turn a success into unmet; `FailureHandler` adds facts, diagnosis, lessons and replans, or `BUDGET_SPENT` plus a blocker. It must not treat a cancellation as a failure or a summary as proof.
12. `OwnerPresentSpeaker` → `CompanionSpeaker` — decides how it sounds. Contract: silent while the owner is away; chat chunks go to everyone, then the SPEECH view to mod clients with the addressee. It must not bypass `ReplyGuard`.

| Hand-off | Invariant |
| --- | --- |
| line → brain | one event per accepted line; a throttled guest line is observed, never answered |
| turn → model | one request in flight; a reply from an older `generation` is discarded |
| model → tools | one TOOL message per call, in order; an error is still a result |
| tool → queue | authority is a principal re-resolved at activation, never a saved level |
| task → event | settled once, after the coordinator's transition has flushed |
| event → goal | a success needs world evidence; a cancellation is not a failure |
| brain → speaker | silence when the owner is away; no internal name or unasked coordinate is spoken |

### Task lifecycle

Every server tick runs the reflexes before the queue: `CombatController` (fight, retreat, eat), `FireReflex` (a burning body or owner), `SelfCareReflex` (a water drop, a milk bucket, a golden apple, a potion) and `RecoveryReflex` (going back for the drops of a death, on a cooldown). A consumable takes a `HoldReason.SELF_CARE` hold for the few ticks vanilla needs — the self-care reflex and `CombatController`'s eating share it — so the running task resumes with its tool in hand; `CombatController.busy()` and `SelfCareReflex.busy()` keep the two from eating at once.

`QueueDriver` selects queued work and interprets plans; when no job is ready, `ExecutionCoordinator` consults `IdleRepairPolicy` for one pending `has_item` blocker with plan repair consent and inserts an `obtain_item` job before it through `JobQueue.insertPrerequisite`, once per blocked job; `ExecutionCoordinator` owns orders, scoped holds, suspension and default activity; `ActiveTaskController` owns the current or frozen task, captures its caller and settings snapshot, enforces timeout, and turns a thrown task callback into `FAILED`. Replacing a task calls `stop` once. If a task starts a replacement during its own tick, the old tick result is discarded after the replacement is installed. Terminal notifications pass through `TaskEventSink` and flush after the coordinator settles the transition, so listeners cannot reenter a half-finished queue update. With nothing to do the coordinator falls back to `FollowTask`, unless free time makes standing still the default (`DefaultActivityPolicy`, asked through `CompanionEntity.mayFollowOwner`). Pausing suspends ticking without losing the task: `CombatController` sets it around a retreat and around a fight it did not order and the companion inventory window owns an independent token. The companion menu takes no hold: the world and the companion keep running while it is open. `TaskPersistenceCoordinator` decodes the versioned execution document, attaches event listeners before notices, rebuilds only tasks known to the current registry, and rejects work whose actor or ephemeral spending authority is no longer valid.

Material the work still needs is not path material. `ExecutionCoordinator.refreshMaterialReserve` composes one `MaterialReserve` on a transition and at most once a second: the remaining queue jobs through `PlanMaterials` (block ids resolved to their drops by `PlanMaterialSource`, so `mine_blocks minecraft:stone` reserves cobblestone) and the running task's own `Task.materialNeeds` (a mining job its remaining target, an obtain job what is still missing), the larger of the two per item. `MaterialPicker.takeCheapest`/`count`/`cheapestPrice` skip reserved stacks and `Scaffold.surplus` honours the larger of the blueprint's need and the plan's, so a pillar or a support fails with the reserved item named (the catch platform names the reserve without the count) instead of eating it; `Navigator` then searches with fewer placeable blocks and prefers the existing `DIG_ASCEND` route, and the model decides whether to mine more or gather something else.

A hand-over the companion performed is evidence. `GiveItemsTask` counts the bag, both hands and matching stacks lying within four blocks (a tool swapped out with a full bag is dropped at its feet), records each dropped stack in the companion's `DeliveredLedger`, and `CompanionGuardFacts.ownerCountItems` takes the larger of the owner's inventory and the ledger's live drops, so a `delivered` goal criterion is met by the drop and lapses once the drop is gone.

Free-time speech uses the pure `CompanionSpeechPolicy` at the existing brain and shift-report boundaries. Outcome-only turns retain their permitted learning tools but do not narrate; direct player replies remain owed, cancellations stay in task history without a model request, and a blocker with the same `ShiftBlocker` key in retained shift history is not reported again, so the same cause on another tree or another tick stays silent. An unchanged plan authority blocker gets another model turn only after its five-minute cooldown; the queue keeps the pending step visible. A teleport, a dismissal or an owner stop bumps the owner's plan epoch, so a late planner reply is neither queued nor allowed to end the shift it was planned for. `FreeTimeDriver` includes recent failure evidence in planner input and renders fixed reports through translation keys: a missing support, a named protected place and an unclimbable tree each have their own line, and anything else keeps the generic one. Every shift emits `shift.start`, `shift.end` (with the diagnosis kind and detail) and, when the owner is told, `shift.report`; a direct owner line is also written as `assistant.direct`. Away summaries retain those keys and primitive arguments in the existing bounded string list, so the owner's client locale resolves them on return.

### Mood, bond and the outline

`features/social/` is pure and holds the affect model. `InteractionStyle` is the owner's choice of how much the companion says (CONCISE/BALANCED/EXPRESSIVE, one bounded clause appended to the tone line, never a permission). `MoodModel` turns observed facts into one of six faces with
hysteresis — ten ticks of danger before it turns `WORRIED` and twenty quiet ticks before it lets go — while `pulse`
and `cue(SpeechCue)` add a bounded eighty-tick reaction to a deed or to something the owner explicitly said. The face
is the only synced value: `DATA_MOOD` (`CompanionEntity.syncedMood`) reaches every tracking client, and
`CompanionRenderer` draws one mark above the head and, for the owner's own companion farther than twelve blocks or out
of sight, sets the render state's outline colour so the vanilla glow pass traces every model part; the owner is found
through the synced owner id (`DATA_OWNER`). The outline switch belongs to the world, not to the client: it is stored
per owner in the world's `CompanionLifeData`, synced as `DATA_OUTLINE` (`CompanionEntity.syncedOutline`), starts off
in every world, and is changed only through the typed CONTROL `ToggleOutline` request sent by the companion menu's
Settings tab or the **Companion outline** key. The decision itself is the pure
`presentation/companion/CompanionOutline.shouldDraw(...)`, so the rule is unit-tested without a frame.

The bond is owner-private and never an accessor. `BondLedger` counts only deeds — shared work, a gift past its
previous peak, a rescue, and an owner hit within the daily cap — with one point of decay per elapsed game day;
`BondRules` holds the windows that decide whether a deed counts, `BondState` is its save shape, and
`BondPrompt.line` renders at most 160 characters of tier, mood and newest reason into the prompt's memory block for
the owner only. `MemoryBook.bond`/`putBond` persist it inside the memory record (format 2), so it survives death,
respawn and a restart, and `/friendai social status` shows the same three reasons to the owner.

### Speaking first

The companion answers by default; it may also start a line, and only about a fact. `server/agent/social/SocialDirector`
runs once a second from `ServerTickPipeline`. It stays silent until the owner's language has been learned from an
owner message; while language is unknown it leaves happenings unconsumed so they can be delivered afterwards. Once
known, it reads the owner's happenings journal — a death, a respawn, a change of dimension, a return after half an
hour, an announced advancement, each recorded by `HappeningFeed` from the Fabric events the server already receives
(the advancement rides a one-line mixin because Fabric has no such event) — and, when the owner is near enough to hear
it, in the same dimension, not in a fight, not hurt and not holding an open container, posts one
`BrainEvent.SocialOpening` for the newest entry nobody has spoken about yet. An entry is marked spoken only when that
line is actually posted, so a quiet window, a fight or a hold cannot swallow it. A line nobody could hear is held for
6,000 ticks and then dropped once. During an active owner job, advancement and low-priority facts are held and ordinary
topics wait; urgent facts remain eligible, and passive following does not count as an owner job. Two lines never come closer than 1,200 ticks; a death already spoken about is never
repeated. When there is no fact to tell it may open a subject of its own: `SocialDirector` first offers facts the
owner stated about themselves — a `PROFILE`, `PREFERENCE` or `PROMISE` whose subject and author are the owner — and
`SocialTopics` renders each one with its source named ("You told me earlier: …"), so a recorded claim is never
presented as something the companion witnessed. `TopicCandidates` picks the first candidate `TopicRing` has not
raised that `BannedTopics` allows and the cadence's question policy permits; the ring stores a stable `fact:<id>` for a
record and the opener text for the bank. When no grounded candidate passes it falls back to `TopicBank`, whose openers
are neutral questions about plans, preferences or work and assert no past event or unseen place. An empty result is
silence: no event, no remembered key and no cadence charge. Ordinary topic openers are suppressed while free-time
autonomy is on, so small talk does not compete with the activity director; journaled facts remain eligible. The chosen
identity is committed only when the event is actually posted. Both the ring and the taste learned from answers live in
the owner's versioned `SocialMemorySave` record (`infrastructure/persistence/social/SocialMemoryStore`), loaded on first
use and saved whenever they change, so a restart neither repeats a subject nor forgets a preference.

A chatter-only batch carries no tools at all: when a `SocialOpening` is batched with nothing but a world notice, a
taught-run outcome, a stop or a successful report, `CompanionBrain` sends `List.of()` schemas and an empty tool-name
set for the turn, so the model can only answer in words. A batch that also reports a failure, a blocked plan, an idle
goal or a shift keeps its tools: the model is never told to repair a plan with nothing to repair it with. `ReplyGuard`
strips the `[silent]` sentinel, ids, coordinates and repeats, and also drops a tool call the model typed into its
message body instead of returning it as a call (`<tool_calls>`, `<invoke>`, `<parameter>`, the `antml:` spelling, the
`<function=name>` form and chat-template tokens such as `<|im_end|>`); a reply that was only markup becomes silence and
is remembered as the sentinel. A late reply dies on the generation counter like any other. The
owner switches it off with `chat.ambientSpeech` (off means the companion answers only) and reads the state with
`/friendai speak status`.

### Death and respawn

`CompanionEntity.die` drops first and captures second. `dropEverythingAtDeath` empties the 27 inventory
slots and the six equipment slots onto the ground at the death spot and clears them in the same pass, so
neither the replacement body nor vanilla's own loot path can hand out a second copy; the
`dropCustomDeathLoot` override stays empty for exactly that reason. `CompanionEntity.saveCarry` then
writes what is still body state — hunger, XP, combat settings, pace and the bounded `SavedExecution`
document parts — into an inventory that is now empty. `CompanionManager.deathOf` adds the dimension,
position, cause, killer and game tick, the UUIDs of the item entities the death spawned, a stack list as
a fallback and a `unrecoverable` flag for lava, fire and the void, and `CompanionCarryData` (world
`SavedData` `friendai:companion_carry`) stores that record with a capped death log under the owner UUID.
Furnace jobs and station leases are not saved by the entity; the manager copies them in memory for a
respawn in the same session.

Going back is `RecoveryReflex`, ticked beside the fire and self-care reflexes: an idle or following body
fetches drops within 24 blocks on its own, and only with `autonomy.enabled` once they are farther away.
It interrupts the runner the way a reflex does, and `RecoverDropsTask` re-checks the dimension, hazard and
the 5,400-tick deadline (vanilla `ItemEntity` lifetime is 6,000), walks to the site with the normal navigator and
only then runs one bounded round that collects the recorded entity ids through `DropCollector`; it reports
"recovered N of M stacks" and clears the record only when the site is resolved or the trip is explicitly abandoned,
so a partial round leaves the rest to a later attempt.
`recover_drops`, `dropped_items` and `forget_drops` expose the same state to the model; the last one sets
the per-owner refusal that both paths honour until the owner reverses it or the next death clears it.

`CompanionManager.tick` replaces the dead body after its unload callback, building the new entity
with the owner, the stored name, the skin store and the bed/shared spawn. It registers the entity,
drops any brain that still points at the dead body (`CompanionSessions.onEntityReplaced`, which bumps
the old generation), applies the saved body (`CompanionEntity.restoreCarry` → `readBody`, so the
queue, plan cursors and eligible task checkpoints restore through `TaskPersistenceCoordinator`) and clears the pending
body. Auto-respawn off and hardcore keep the record instead: the next `summon` applies it, and
`dismiss` clears it because dismissal already drops the inventory. A restored free-time plan keeps
its id and `free time: ` goal, so `FreeTimeDriver` reopens the shift; the driver ignores a
`isDeadOrDying()` body so a zero-health corpse cannot trigger a reflex that cancels it.

### Companion menu

The client subscribes with a typed CONTROL-family request frame; `ProtocolRequestDispatcher` passes the authenticated request to `DebugStream.openMenu`, which subscribes the player and sends the first snapshot in a `ProtocolViewS2CPayload`. `UNSUBSCRIBE` goes through `DebugStream.closeMenu`, the same path a disconnect and the ten-tick sweep take. The map tab receives its own bounded CONTROL frame (operation 129): `TerrainMapView` carries at most 128 seeded, spaced cells plus 32 sites and 32 roads of the player's current dimension, never the full grid; `TerrainMapProtocolCodec` bounds the frame and `MapTab` draws it; the record itself lives in `features/cartography/view`, the one package presentation may read from a feature. `DebugStream` pushes framed control views every 10 ticks; `SnapshotBuilder` builds them for the requester’s own companion, and a frame the encoder rejects closes that viewer’s menu with a warning instead of escaping into the server tick. Everyone sees status and task history; the brain log, prompt, perception text and tool names are operator-only (`DebugAccess`, checked on the server). The Memory and Places tabs send typed MEMORY and PLACES requests and receive correlated protocol views; rename and delete use typed place operations.

### Instruction skills and self-teaching

`SkillService` captures the authenticated caller, current message/task, turn kinds, memory description/profile and the effective builtin/global/owner skill records before provider work starts. `CompanionBrain` captures one `SkillTurnSession` per turn; `CompanionSessions` enriches normal/free-time planner inputs through `PlannerAdapter`. Selection is explicit request, always-on, turn-kind match, then literal trigger; within one tier owner/model records precede builtins, then ID order breaks ties. Disabled/pending records never qualify. A recovery turn — a failed or blocked plan — adds that plan's failure lines to the text the triggers match, so the repair advice reaches the model on the turn that needs it while ordinary chat keeps the smaller selection. The instruction slice is at most `min(skills.promptBudget, agent.promptBudget / 5)` (4,096 characters by default, still capped when the agent budget is unlimited). The packaged catalogue holds up to 64 builtins, including `skill-authoring`; the index loaded by `BuiltinSkills` is the authoritative list, and every builtin title key is derived from its id by one convention (`BuiltinSkills.titleKey`). Whole cuttable sections lose to mandatory rules. Final included IDs/character costs and provider token usage are operator diagnostics.

`use_skill` delivers an eligible explicit instruction once and displaces automatic guidance if needed. `list_skills` returns one bounded page of the owner's catalogue (id, name, source, activation, version, enabled state and a one-line description, never a body) and `skill_help` returns the shipped `skill-authoring` procedure plus limits generated from constants and config; both are owner-only reads available on every turn, while writing stays gated. Accepted terminal goal transitions and finished shifts post a `SkillOutcome`; only that outcome turn offers `manage_skill`. A guest sees only the public builtins `verification`, `trade-etiquette` and `social-and-privacy`. The server rechecks owner/source/outcome/generation, six writes per rolling hour and two per outcome, persists the ledger, and requires owner approval for new model records by default. Cancel/dismiss/logout invalidate the brain context. Personal facts still use `remember` and the existing five categories. A skill cannot execute text or alter a tool's AccessLevel.

`SkillsViewStream` sends only the authenticated sender's paged catalogue and requested body. The Skills tab and the Description editor share bounded server actions with `/friendai skills ...` and `/friendai description ...`. Global writes require the separate operator command branch; they grant no access to other owners' books. Client saves carry request IDs so cached/unsolicited views cannot acknowledge a newer draft. Editor screens keep the menu subscription. Known configured secrets are checked again before prompts, views and exports; raw skill tool arguments/results are omitted from logs.

### Configuration

`ServerRuntimeFactory` builds the service graph for one `MinecraftServer`; the lifecycle registry removes it before idempotent close. `ServerServiceGraph` loads `config/friendai-server.json` through `ConfigStores.server`. The client uses `ConfigStores.client` through `ClientConfigurationCoordinator` for `config/friendai-client.json` and the same server factory for editable integrated-server settings. Supported old schemas traverse the complete adjacent migration chain on a JSON copy, deserialize and validate, merge defaults while retaining unknown fields, create a unique versioned backup of the exact source bytes, check that the source has not changed, then replace atomically. Backups and replacement bytes are flushed before replacement. Server `persona` becomes `description`; client legacy recognition/provider layouts and voice prefixes become the current voice schema. Explicit resource permissions and observation radii are retained. Failed upgrades preserve the original and block writes; reloading retries. Unknown/future versions use server defaults in memory and remain read-only. The screen owns widgets and drafts, while the coordinator validates/persists and the integrated adapter schedules apply on the server thread. `ServerConfiguration` resolves the config and publishes one immutable `ServerSettings` snapshot per server before notifying loaded task runners. Active tasks retain their start snapshot; tasks created after a reload use the new settings. `ServerConfig.activeProfile` → `toLlmProfile` → `LlmClient`; a reload rebuilds the client and registry-bound tools. Owner/world record formats are not migrated by this mechanism.

### Speech recognition

The client captures audio only while push-to-talk is held, resolves the selected provider (a `LocalSttCatalog` entry or a cloud preset), checks readiness, and sends a typed SPEECH-family request frame only if the server negotiated that capability. A clip-only local model (`WhisperLocalStt` or the sherpa offline transducer) transcribes the finished clip on a worker; Nemotron uses `StreamingSpeechToText`, so `MicCapture` offers ordered chunks to a bounded queue while the HUD shows a capped local partial, and exactly one final transcript is produced on release. `LocalSttBundleManager` downloads every entry from its pinned revision into a staging directory, verifies each file's size and SHA-256, publishes atomically and writes a marker; the recognizer re-hashes once per process before loading native code. A changed, cancelled or disconnected press invalidates its partials and final callback, and every capture carries a token so only the operation that started it may stop the microphone; a preview that finishes after another recording began cannot cut it short. An appearance upload is bound the same way to the session that started the fetch. The receiver captures the active session and dispatches on the server thread; stale transcripts from an old connection are dropped. Local audio never leaves the machine; a cloud provider uploads the recording only while it is selected. New bundles live in `<gameDir>/friendai/models/stt/<id>/`, legacy Whisper files stay in `<gameDir>/friendai/models/`, and an unknown configured id is reported rather than replaced.

### Speech output

Streamed replies use the same family: `CompanionSpeechStreamView` (operation 129) carries `streamId`, `sessionId`, `sequence` and `last`; the client feeds it to `SpeechStreamBuffer`, which orders and de-duplicates sentences and drops a stale session. `voice.streamReplies` buffers the sentences locally when off; stopping, a new message or a disconnect invalidates the buffer and reports one incomplete-stream toast. `CompanionBrain` may release a complete sentence through the existing `ReplyGuard` before the provider finishes; the full response stays authoritative and tool calls wait for it.

`CompanionSpeaker` sends each reply as a typed SPEECH view inside `ProtocolViewS2CPayload`; the last two values are filled from the speaking entity and `chat.hearingRadius`. The client’s `SpeechRuntime` cleans and splits the text, then either synthesizes locally with sherpa-onnx (`client/audio/LocalTtsEngine`, a downloaded Piper voice) or calls a cloud engine (`infrastructure/speech/CloudTtsEngine`: OpenAI, ElevenLabs or Yandex) through `TtsClient` and `VoiceHttp` on a worker thread. `SpeechPlayback` plays the clip through the chosen device, opened with a small buffer so a change is heard without the device’s default delay; when **Voice comes from the companion** is on (`voice.tts.spatial`), it mixes the clip to stereo in 20 ms blocks and ramps each channel from the previous block’s gains to the `SpatialAudio` gains that `SpeechRuntime.tick` recomputes every client tick, so the pan and attenuation follow the player without steps or clicks, and a reply whose companion is not in the client’s level is dropped. With the setting off the clip plays centred at full volume. Synthesis is off by default; the settings live under `voice.tts` in the client config. `SpeechGate` drops a frame while recording or when it is addressed to another player and “speak for other players” is off. Push-to-talk and the **Stop speaking** keybind stop playback. Disconnect invalidates the session token, closes the microphone and playback, clears connection-scoped views, and makes late recognition/synthesis callbacks stale; the worker and model downloads remain application-scoped. Native whisper/sherpa initialization is guarded to the client environment. Only cloud engines send the reply text off the machine, keys travel in headers only, and paid requests are never retried automatically.

### Measuring whether it feels smarter and quieter

The numbers ride on one chain of existing objects, and they are only worth reading where that chain already leaves
text behind. A turn arrives as a sealed `BrainEvent` — `PlayerSaid`, `TaskFinished`, `TaskCancelled`, `PlanFinished`,
`PlanBlocked`, `GoalTick`, `SocialOpening`, `WorldNotice`, `SkillOutcome`, `FreeTimeShift` or `IdleNudge` — whose
`toPromptLine` is what the model reads. `DebugLogObserver` also writes every one of them verbatim to the owner's
`DebugLog` as a TASK line (a `PlayerSaid` as USER), the raw assistant text as ASSISTANT, each tool call and result,
the provider error and token usage. That bounded log, `TaskRecord` history (SUCCESS, FAILED, CANCELLED) and the goal
and free-time files are the measurement surface; the Log tab and the `/friendai diagnose` bundle read the same state.

The honest half of the chain is the evidence `SessionEvents.extra` builds. `OutcomeFacts.snapshot`
captures a `WorldSnapshot` before and after a task, and `OutcomeChecker.check` diffs it — inventory deltas, empty
slots, health, food and owner distance, at most `MAX_FACTS` (eight) — then asks `GoalBoard` whether the criteria of
the goal that owns the plan hold. `Criterion` pairs text with an optional `Guard` (`has_item`, `inventory_space`,
`health_at_least`, `owner_within`, `block_within`, `dimension`, `all_of`/`any_of`/`not`, `biome`, `fluid_ahead`,
`distance_travelled`, `time_elapsed`); a failing guard and a text-only criterion both count as unmet. `FailureHandler`
turns that into the suffix the model reads: `facts:`, `diagnosis:`, `tried:`, `unmet:`, `blocker:` or the replan-budget
notice, and `all criteria confirmed: call finish_goal` on success. A `finish_goal` call posts the terminal
`SkillOutcome` for `goal:<id>` (`GOAL_SUCCESS` or `GOAL_FAILURE`). `GoalTick` wakes an idle companion with its unmet
list and answers a silent model with the blocked line itself, and `QueueText` renders the prompt and status view (`Task queue: N running, N pending`, `Blocked: #id ...`,
`plan #id "...": current <path>`) so what the owner sees can be compared line for line with the log. `GoalBoard.finish`
takes the model's word and does not re-check criteria, which is exactly why false completion has to be observed
rather than trusted.

| Metric | How it is counted today | Where to read it |
|---|---|---|
| Verified-goal completion rate | Counter: `LoopMetrics.goalVerified()`/`goalUnverified()` per terminal goal, in the `loop: …` line. Each terminal goal also leaves one TASK line `[event] completed work outcome: GOAL_SUCCESS` or `GOAL_FAILURE`, with its `facts:`/`unmet:` evidence on the lines just above it; count the terminal lines per run. | Operator Log tab (`TASK`), `log.txt` in `/friendai diagnose`. |
| False completion claims (target: zero) | Counted and enforced: `finish_goal done:true` is refused while a world-checkable criterion does not hold, and each refusal increments `LoopMetrics.completionRefused()`. | `TOOL_CALL` and `TASK` lines in the same log; the goal's criteria before it left the board. |
| Repeated failed remedy rate | Counted: `RecoveryAdvisor` reports how many already-tried remedies it dropped (including the build wording, which is normalised before the check) and `FailureHandler` feeds that into `LoopMetrics.remedyRepeated()`, reported in the `loop: …` line. | The `MANUAL` line `loop: … repeated remedies` and the goal's lessons in `goals/<uuid>.json`; `TASK` lines still show each `tried:` text. |
| Owner clarification rate | `not counted yet`. `IdleNudge` and `GoalTick` each post one TASK line, and a question is one ASSISTANT line; nothing pairs either with the turn route. | `TASK` (`IdleNudge`/`GoalTick`) and `ASSISTANT` lines. |
| Unnecessary status messages | `SocialActivity.summary()` counts unprompted lines (ordinary and urgent), held, dropped, owner messages and the events `HappeningFeed` journaled, per owner, written every 24,000 ticks — ambient speech only. Replies that narrate steps are `not counted yet`. | The `MANUAL` line `social activity: ...`; `ASSISTANT` lines for the replies. |
| Time from owner interrupt to stopped work | `not counted yet`. `LogEntry.timeMillis` is recorded but neither the Log tab nor `log.txt` prints it; the stop itself is one `[event] task #N ... cancelled` TASK line and one CANCELLED `TaskRecord`. | Stopwatch from sending the order to the `cancelled` line; Tasks tab history. |
| Autonomous duplicate-work rate | `not counted yet` as a rate. Finished shifts are `ShiftRecord`s in `FreeTime.history` (capped at five: goal, ok/failed, summary) and `/friendai freetime status` prints "Finished shifts remembered: N"; nothing detects a repeat. | `/friendai freetime status`, `free-time/<uuid>.json`, Tasks tab history. |
| Recovery after reload | `not counted yet` as a rate. `TaskPersistenceCoordinator.restore` returns `RestoreReport(restored, rejected)`; every rejection is logged server-side as `Execution restore: ...`, a job whose tool disappeared is also posted to the brain as a `WorldNotice`, and restored jobs reappear in the queue. | Server log; `queue.txt` in the diagnose bundle; Tasks tab. |

**The fixture set.** Run it before and after a change on the same save copy, provider and model, `agent.promptBudget`
and `skills.promptBudget`, language, `goalTickSec`, `chat.ambientSpeech` and `autonomy.enabled`; copy the save rather
than re-summoning, and start each run with an empty owner log. Keep the `/friendai diagnose` bundle
(`summary.txt`, `log.txt`, `tasks.json`, `queue.txt`, plus `chat.txt` when chat is included) with the fixture name and
date, and compare only like with like.

1. Verified quantity goal: stand next to trees and say "Friendai, mine 3 logs". Expect one goal with a `has_item`
   criterion, then `facts: +3 ...`, `all criteria confirmed: call finish_goal`, `finish_goal done:true` and one
   `GOAL_SUCCESS`. Count terminal goals, claims made before the criterion held, and narration lines.
2. Partial completion: ask for a build or a count the nearby world cannot supply in one trip (a 3×3 stone platform
   with no stone in the bag). The gather step runs first, the log shows `unmet:` or `not proven yet:`, and nothing is
   reported as done until the criterion holds.
3. One remedy, then a blocker: ask it to reach something it cannot (a tree across a ravine, an ore behind a wall).
   Expect one `PlanBlocked`, one `diagnosis:`, one `tried:` and one `queue_edit` repair; when the repair fails,
   `blocker:` names the cause instead of repeating the same remedy.
4. Interruption: start "mine 15 logs" in a forest and say "stop" as the first log is cut. Time the stop with a
   stopwatch (entry times are not printed), confirm no later TOOL_CALL, and check the reply is one line.
5. Reload: with a plan mid-step, leave and rejoin or restart the server. Read the `Execution restore:` lines and the
   queue after rejoining; the job resumes and reports once, a missing tool produces the repair notice, and a resource
   search is cancelled as a restart victim by design.
6. Free time: `/friendai freetime on`, stay within hearing, and go quiet for a recorded hour. Read
   `/friendai freetime status`, count shifts, how many repeat a recent activity, and any failed shift.
7. Silence: with `chat.ambientSpeech` on, stay near and silent for twenty minutes. Read the `social activity:` line
   (ordinary, urgent, held, dropped, owner messages), ignore one question and confirm it is not repeated inside the
   backoff, then answer the next one.
8. Second language: repeat fixture 1 in Russian, and open the menu in both UI languages. The reply follows the
   owner's language, the log evidence stays English, and the same guard (`has_item`) is what makes the criterion
   checkable in either.
9. Menu agreement: with a goal open and a task running, compare Overview, Tasks and Feeling with the log — the task
   line, the `TaskRecord` history and the criterion (not proven → met) must be the same state, before and after a
   relaunch.

A change counts as an improvement only when verified goals rise while false claims, repeated remedies, clarifications,
narration, stop latency, duplicate shifts and restore rejections do not; more model calls or more chat are not a gain.

**The headless half.** The nine fixtures above also run without a world, against the real `CompanionBrain` and the

## Data and persistence

The durable diagnostics tree is not an owner store, and it is not shared between worlds. `debug/LogPaths` is the
single derivation from a world or game directory to a log path: the server writer, `CompanionSessions.logRootFor`
(which feeds `logs_search`), the `/friendai diagnose` bundle and `/friendai logs path` all resolve their root there, so
a companion can only read the world it lives in. The root `debug/LogWriterService` writes a world's `server/`,
`owners/<uuid>/` and `diagnostics/` JSONL with one daemon thread into `<world>/friendai/logs/`, rotates at
`logging.maxFileBytes`, prunes by `logging.maxTotalBytes`, `retentionDays` and `maxSessionsPerOwner` (per world), and
writes a generated `.md` digest beside each closed file; every header names its world. Retention counts every file on
disk — open ones included — and treats a digest as part of its JSONL: the two are deleted together, an orphan digest
goes on its own, and a set of open files that alone exceeds the cap is reported once instead of growing silently. A day
rollover closes the previous day's writers, so they stop being protected from pruning. The client writer keeps
`client/` at `<gameDir>/logs/friendai/`, where `debug/LogWorldIndex` appends one line per world load and close so a
deleted world still leaves a trace. Trees written before 0.203.0 at the shared root are never read or pruned.
`LogPipeline` redacts and fans records out; `FriendaiLogAppender` adds `warn`/`error` from `friendai*` loggers.

Owner-file persistence uses the pure `StoreCodec<T>` contract (including bounded `Reader` decoding) and
`StoreWriteStatus` with typed failure/read-only reasons. One runtime view, `debug/StoreHealth`, reads those statuses
through `ServerRuntime.storeStatuses()`: it reports a store, owner, saved revision and reason only when the health
changes (entering a failure or read-only protection, changing it, or recovering), so a full disk is visible as one log
line instead of silent lag, and the same lines appear in `/friendai diagnose`; it never prints a path, a value or an
exception message and never writes anything itself. `ServerServiceGraph.storeStatuses()` is the one store list: it
covers memory, the transcript, companion profiles, per-companion and operator instruction skills (reported apart as
`skills` and `skills-server`), goals, free time, social memory, terrain, routines, knowledge, places, placed blocks and
trading, and `OwnerRecordFlush` reads that same view instead of keeping a second list. Appearance (`SkinStore`) and
blueprints write synchronously and hand a failure to their caller, so they carry no stored status; a source test fails
when a store the graph builds is neither reported nor documented as untracked. `OwnerFileStore<T>` lazily loads records and captures
immutable UTF-8 bytes plus their revision on the server thread. At most one snapshot per owner is pending;
a completion records only its own saved revision. A later server-thread flush captures any newer revision,
and final close repeats that capture/wait cycle until settled, failed, or its 30-second bound expires.
Normal `flushAll` and five-second debounce flushes never wait for disk. Queue rejection leaves records dirty
with `QUEUE_FULL`, allowing the next ordinary flush to retry. Status contains no paths, values or exception text.

`ServerServiceGraph` acquires one bounded, single-thread `OwnerStoreWriter` through `RuntimeResources`
before acquiring stores. Memory, profiles, goals, free time, routines, social memory, places, placements, knowledge, trading,
and both instruction-skill scopes borrow it; reverse-order `ServerRuntime` teardown closes and flushes these stores
before closing the writer once. Standalone test stores may explicitly own a writer. Store close is idempotent
and never closes a borrowed writer.

Missing files stay absent until mutated. Corrupt files are backed up and remain read-only even when the backup
succeeds; failed backups and failed reads also preserve the original in read-only mode. Unsupported and oversized
files remain read-only. Atomic replacement falls back to replacement move only when atomic move is
unsupported. Before this non-atomic fallback, the writer preserves a separate recovery copy of an existing
target; failed replacement restores that target, and failed restoration retains the recovery copy. Successful
replacement/restoration removes the temporary recovery copy. Failed writes leave the latest revision dirty. The
package-local `OwnerFileOperations` seam makes backup, read, write and move failures deterministic in tests.
Domain wrappers accept an `OwnerFileStore.Factory` construction boundary, allowing their actual codecs and
owner/server scopes to run the same injected-failure contract without exposing file operations to features.
Trading uses `OwnerFilePolicy<TradeBook>` for bounded snapshot encoding and protected-record-aware eviction,
and a `StoreCodec` reader path that parses under the shared 8 MiB byte bound. Unsupported and oversized trade
files remain read-only until explicit repair, which makes a fresh backup before allowing replacement.

## Network protocol

`server/net/FriendaiNetworking` registers the versioned protocol payloads. The Fabric wrappers live in `transport/payload/`; body formats and bounds live in the pure engine `protocol/` package.

| Direction | Payload | Purpose |
|---|---|---|
| S2C | `ProtocolHelloS2CPayload` | Bounded version and capability offer sent after join. |
| C2S | `ProtocolAcceptC2SPayload` | Accepts the negotiated version and capability set. Requests remain closed until the server accepts it. |
| C2S | `ProtocolRequestC2SPayload` | One bounded frame containing version, explicit family and operation IDs, a per-connection monotonic request ID, and a typed C2S body. |
| S2C | `ProtocolViewS2CPayload` | One bounded typed view frame with family/operation metadata and request correlation. Carries control, memory, places, instructions, trading, debug and speech views. |
| C2S/S2C | `SkinUploadC2SPayload`, `SkinRequestC2SPayload`, `SkinS2CPayload` | Existing typed appearance data; each direction is accepted or sent only after handshake negotiation includes the `friendai:appearance` capability. |

The server creates a pending session per `ServerPlayer` and sends hello only when both bootstrap directions are available. The client validates the offer and sends accept. Until that succeeds, all request and appearance handlers reject work. A pending handshake expires after 100 server ticks. Vanilla replaces the `ServerPlayer` instance on respawn and on the End-portal return while the connection stays, so `ServerPlayerEvents.AFTER_RESPAWN` rebinds the admitted session to the replacement with the same session id; the client does not negotiate again. Each admitted request must match the current player connection, a negotiated family, the next request ID, the frame bounds and the request codec; the server dispatches it on the server thread. Client receivers hop to the client thread, verify the captured connection session and negotiated family, then apply only matching correlated views. Skin bodies remain separately typed but share the handshake and capability gate.

`ProtocolCapabilities.friendai()` defines the advertised feature set. Bootstrap validation caps it at 32 unique entries, with each UTF-8 capability name at no more than 64 bytes. Unknown versions, malformed frames, unsupported family/operation pairs, stale sessions and out-of-sequence requests are dropped; a failed bootstrap disconnects the peer.

The MEMORY family also carries the recent-chat rows of the owner's own transcript (newest 20, at most 50 on the wire) and a `TranscriptClear` operation that empties only the sender's transcript; the server applies it on the sender's own book.

The companion inventory/equipment window uses a vanilla container menu (`menu/FriendaiMenus`), not a custom payload.

## Access and permissions

- `AccessLevel`: `GUEST < TRUSTED < OWNER`; each `Tool` has a minimum access, and `ToolRegistry.run` filters before execution.
- Memory rights: `AccessResolver` classifies the caller; `MemoryPolicy` decides read/write/forget per subject; a guest only sees facts about themself. Trust changes need the owner's confirmation (`TrustConfirmations`).
- Operator-only: brain log, prompt, perception text and debug tools (`server/net/Operators`, `debug/DebugAccess`); `/friendai reload` requires gamemasters.
- The movement debug stream (`server/net/MovementDebugStream`) combines the active task's on-demand work snapshot with independent route obstacle cells. Its append-only optional codec section preserves true per-status counts when cells are capped; the client renders only nearby/in-front work cells. The overlay is a per-connection switch on the Settings tab: it is off whenever a connection starts and is not stored in `friendai-client.json`.
- Owner-only: instruction skill CRUD, approval, description and owner profile. The sender selects their own book; no payload selects an owner UUID. Custom instructions/profile details never enter guest/trusted prompts.
- Owner-only: the companion inventory window (owner, same dimension, within 8 blocks, alive).
- World protection: `CompanionHands.canInteract` asks `level.mayInteract` through a fake player; build/break blacklists come from `ServerConfig` (the owning server's `ServerSettings` snapshot and pathing blacklists).


Planner-only gateway calls use completeJson: the optional request flag emits JSON mode for OpenAI Chat/Responses, Gemini and Ollama; Anthropic and custom gateways retain prompt-only behavior. Ordinary brain turns keep prose/tool output. Planner attempt events and queue dispositions use the operator-only PLANNER log kind with bounded redacted replies; owner status and menu diagnostics show the effective planner model. Config schema 15 adds total planner attempts and validates profile selection; schema 16 adds the free-time watchdog timeout.
